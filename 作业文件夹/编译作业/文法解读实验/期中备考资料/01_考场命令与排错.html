编译、运行与机房操作

1. 先分清你在编译什么

parser.c 等文件是你写的“编译器程序”的源代码。GCC 把它们编译成 compiler.exe。testfile.txt 则是交给这个编译器分析的 SysY 程序。

parser.c + token.c + syntax_tree.c + error_list.c
                     ↓ gcc（编译并链接）
                 compiler.exe
                     ↓ 运行，读取当前目录的 testfile.txt
          lexer.txt / parser.txt / error.txt

修改 .c 或 .h 后必须重新编译。只修改 testfile.txt 时，直接重新运行 exe 即可。本阶段不会执行 SysY 程序中的 printf；它只分析程序，写分析结果。

2. 机房环境说明中的事实

环境 新主楼/央财 新北
CLion 2019.3.6 2019.3.6
CMake 3.28.3 3.28.3
GCC 11.2.0 11.4.0
Clang 12.0.0 12.0.0，LLVM 环境在 WSL

说明要求 CMake 使用 -G Ninja。当前任务是 C 编译器的前端扩充，下面的 GCC/CMake 命令即可完成构建。PDF 中 libsysy、llvm-link、lli 那组命令用于运行生成的 LLVM IR，不属于本次已给出的词法/语法范围。

3. PowerShell：推荐先掌握这套

假设你将本资料解压到 D:\midterm，其中有 starter 文件夹。路径是示例，应替换为实际位置。

cd 'D:\midterm\starter'
Get-Location
Get-ChildItem
gcc --version
gcc -Wall -Wextra -std=c11 parser.c token.c syntax_tree.c error_list.c -o compiler.exe
$LASTEXITCODE

确认编译结束且 $LASTEXITCODE 为 0，再运行：

.\compiler.exe
$LASTEXITCODE
Get-Content .\lexer.txt
Get-Content .\parser.txt
Get-Content .\error.txt

逐行执行；不要把 Markdown 的三反引号复制进终端。$LASTEXITCODE 是上一次本机程序的退出码，要紧接 gcc 或 exe 查看。退出码为 0 不保证输入语法正确：该旧版 main 即使普通语法分析失败也可能返回 0，判断还要看 error.txt、parser.txt 和调试信息。

参数解释：-Wall -Wextra 打开常用警告；-std=c11 按 C11 编译；四个 .c 都要参与；-o compiler.exe 指定生成文件名。头文件由 #include 引用，不单独列在编译命令里。

如果编译失败，不要运行旧 exe。考试时不必加 -Werror，它会把警告也当成编译错误；本资料自动验证时使用它检查示例质量。

4. cmd：不要混用 PowerShell 语法

cd /d D:\midterm\starter
dir
gcc --version
gcc -Wall -Wextra -std=c11 parser.c token.c syntax_tree.c error_list.c -o compiler.exe
echo %ERRORLEVEL%
compiler.exe
echo %ERRORLEVEL%
type lexer.txt
type parser.txt
type error.txt

cmd 用 cd /d 同时切换盘符和目录；PowerShell 的 cd 不需要 /d。带空格的 cmd 路径加双引号，如 cd /d "D:\my project\starter"。PowerShell 使用 $LASTEXITCODE，cmd 使用 %ERRORLEVEL%。

5. CMake 与 CLion

starter 和每个示例都带有这个 CMakeLists.txt：

cmake_minimum_required(VERSION 3.16)
project(midterm C)
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
add_executable(compiler parser.c token.c syntax_tree.c error_list.c)
if(CMAKE_C_COMPILER_ID MATCHES "GNU|Clang")
    target_compile_options(compiler PRIVATE -Wall -Wextra)
endif()

在包含 CMakeLists.txt 的目录运行 PDF 指定的构建方式：

cmake -B build -S . -G Ninja
$LASTEXITCODE
cmake --build build
$LASTEXITCODE
.\build\compiler.exe

只有上一条成功才执行下一条。-B build 指定构建目录；-S . 指定当前源代码目录；-G Ninja 选择生成器。exe 放在 build 下，运行时仍站在项目根目录，从而读取根目录 testfile.txt。cmd 运行写 build\compiler.exe。

CLion 中打开包含 CMakeLists.txt 的文件夹，检查 Settings → Build, Execution, Deployment → Toolchains 中 C 编译器是否可用，重新加载 CMake。运行配置中的 Working directory 设置为含 testfile.txt 的项目根目录，程序参数留空。IDE 内终端使用的 shell 可能是 cmd 或 PowerShell，按其语法执行。

若 build 已经用其他生成器配置，换一个未使用过的目录即可：

cmake -B build_ninja -S . -G Ninja
cmake --build build_ninja
.\build_ninja\compiler.exe

机房有 GCC 不等于当前终端 PATH 已配置 GCC。gcc 找不到时，先查看 CLion Toolchains 中实际编译器路径，使用那个 gcc.exe 的完整路径。PowerShell 示例（路径必须换成真实路径）：

& 'C:\实际工具链目录\bin\gcc.exe' -Wall -Wextra -std=c11 parser.c token.c syntax_tree.c error_list.c -o compiler.exe

这里 & 用来执行引号中的程序路径。cmd 则直接写双引号括住的 exe 路径，不加 &。不要猜测机房安装目录。

6. 完整语义版本的编译命令

如果你是在原来的 词法分析 文件夹中操作，当前 parser.c 还依赖 symbol.c 和 semantic.c，命令是：

gcc -Wall -Wextra -std=c11 parser.c token.c syntax_tree.c error_list.c symbol.c semantic.c -o compiler.exe
.\compiler.exe

这条用于原工程；四文件命令用于资料包 starter/examples。不要只漏掉链接文件来“关闭语义”，那会出现 undefined reference。不要使用 gcc *.c：原目录还包含 lexer.c 和多个 *_test.c，它们也定义 main，容易造成 multiple definition of main。

7. 调试开关与输出

gcc -Wall -Wextra -std=c11 -DPARSER_DEBUG_ENABLED=1 parser.c token.c syntax_tree.c error_list.c -o compiler_debug.exe
.\compiler_debug.exe

调试输出包括 token 总数、各 token 行号、CompUnit 成功与否和剩余 token。失败的外层函数会 rollback，所以最后显示的位置可能已经回到开头，不能直接当成真实错误位置。此时在新分支失败前打印当前 token 到 stderr，或设置断点观察 pos。

提交前重新使用普通编译命令，确认没有新增调试 printf 混入规定输出。PARSER_OUTPUT_ENABLED=0 关闭语法文件输出，通常不用于语法考核；关闭时也不会帮你清理旧文件。

8. 常见故障对照

表现 优先检查
gcc 不是命令 PATH/CLion 工具链，使用已安装 gcc 的真实路径
cannot open source file / No such file 当前目录是否有四个 .c，文件名是否正确
undefined reference to addToken 等 是否遗漏 token.c/syntax_tree.c/error_list.c
undefined reference to analyzeSemantics 使用了完整版本，应链接 semantic.c 和 symbol.c
multiple definition of main 是否用了 *.c，把测试/独立 lexer 一起编译了
implicit declaration / conflicting types 新函数是否在调用前声明，返回值与参数是否一致
cannot open output file / Permission denied 旧程序是否还在运行、被调试器占用，先停止再构建
无法打开 testfile.txt 当前工作目录错误；文件可能实际叫 testfile.txt.txt
exe 没有终端输出 正常，去看三个输出文件
lexer.txt 正确但 parser.txt 为空 检查 error.txt、语法入口/分派/回退与调试信息
error.txt 空但 parser.txt 也空 可能是未恢复的语法失败或其他词法失败，不代表成功
修改后结果没变 是否编译失败仍在运行旧 exe，是否修改了另一份副本
运行一直不结束 循环是否没有推进 token，或恢复后反复停在同一位置

最小自检输入：将以下内容保存为 UTF-8 无 BOM 或纯 ASCII 的 testfile.txt（Windows PowerShell 5 的默认重定向可能写出 UTF-16，优先用编辑器保存）：

int main() {
    return 0;
}

预期 error.txt 为空，parser.txt 最后有 <MainFuncDef> 和 <CompUnit>，lexer.txt 以 INTTK int 开始。BOM 可能被当前词法器当成未知字符；看起来内容正确却失败时检查编码。
